# 仓库结构与开发规范

> 2026-11-15 状态说明：本文保留跨仓库设计与历史阶段表述。当前 Core 实现、实际字段及尚未交付事项以[实现状态](../implementation-status.md)和其链接的接口契约为准；本轮未编译或运行测试。

本文所有程序目录树均为建议结构，当前仅维护五个仓库的计划、协作文件和许可证，不生成程序骨架。功能按模块逐步加入，不一次性创建大量空目录。

公共文档统一存放在 `ShitBotUltra`：`plan.md` 为索引，`AGENTS.md` 直接承载公共代理规范，`agent.md` 只保留导航，`CONTRIBUTING.md` 为提交与 PR 规范。CLI、Desktop、Minecraft、MC API 的 `plan.md` 只列自身任务并链接公共计划；本地 `AGENTS.md` 写清可直接执行的阶段限制、组件边界及公共规范入口，不依赖跨仓库自动发现。每仓库单独保留完整 `LICENSE`，统一说明见 [docs/licensing.md](../licensing.md)。

业务模块内部按实际规模使用 `service.go`、`model.go`、`repository.go` 等文件，不必再套多层“控制器 / 管理器 / 服务工厂”。跨模块依赖有明确方向；业务包不导入 UI、CLI 参数解析器或数据库具体驱动。

**跨仓库边界**：CLI 调用公开 `runtime`，自定义 Go 适配器使用公开 `sdk/adapter`；两者均不导出业务实现。参数与返回值必须能从外部命名，禁止泄漏 `internal` 类型。业务不导入某个适配器包，组合入口负责注册与组装。插件及模板契约见[扩展计划](06-扩展接口与数据导入.md)。[Go 官方模块目录指导](https://go.dev/doc/modules/layout)

**WebUI 打包**：前端源文件归 Core 仓库所有，固定 lockfile；发布 Core tag 前生成 `internal/webassets/dist/` 并使它包含在该 tag 的 Go module 中。CLI 固定依赖该 Core tag，即可在自己的可执行文件中携带同版本 WebUI。构建产物应记录来源版本及资源摘要；不能只有维护者电脑上的未跟踪 `dist/`。不使用跨仓库 `../webui/dist` 的 `go:embed` 路径，不依赖运行时 CDN 或启动时下载前端。[embed 路径规则](https://pkg.go.dev/embed)

## 2. CLI：ShitBotUltra-CLI

```text
ShitBotUltra-CLI/
├─ cmd/sbu/main.go               # 只转交入口、处理退出码
├─ internal/
│  ├─ cli/
│  │  ├─ options.go              # 标准库 flag：启动参数、帮助与版本
│  │  ├─ launch.go               # 无参数启动 / serve 共用的运行入口
│  │  ├─ config.go               # Desktop 所需的只读离线配置校验
│  │  ├─ migrate.go              # 后续显式导入入口，调用 Core 服务
│  │  └─ update.go               # 检查 / 升级入口及版本进度提示
│  ├─ client/                    # 已运行 Core 的管理客户端
│  ├─ instance/                  # 发现实例、受限状态文件、锁
│  └─ output/                    # 控制台日志、地址提示和机器输出
├─ packaging/
│  ├─ systemd/
│  ├─ windows/
│  └─ container/
├─ docs/
├─ .github/workflows/
├─ go.mod                        # 固定 Core 的已发布版本
├─ go.sum
├─ LICENSE
└─ README.md
```

CLI 按 [LuckyLillia.CLI](https://github.com/LLOneBot/LuckyLillia.CLI) 的轻量启动器使用形态规划：直接运行 `sbu` / `sbu.exe` 即启动 Core，显示控制台日志与本机 WebUI 地址，按 Ctrl+C 优雅停止；`sbu serve` 是显式等价入口。首次生成的配置默认开启本机 WebUI，已有配置保留其设置；Desktop 后台启动时明确传入 `--no-webui`，附加已有实例时保留其设置。

主要交互是 `--config-dir`、`--webui`、`--no-webui`、`--debug`、`--help` 和 `--version`，配置与业务管理主要在 WebUI / Desktop 完成。使用 Go 标准库 `flag.FlagSet` 解析，少量维护入口手动分发；不引入 Cobra。LuckyLillia.CLI 的 Rust 入口同样直接读取参数并处理启动流程，Ultra 借鉴这种轻量组织方式，继续在本进程调用 Go Core。[参考入口](https://github.com/LLOneBot/LuckyLillia.CLI/blob/main/src/main.rs)、[flag 文档](https://pkg.go.dev/flag)

`options.go` 使用可返回错误的参数解析方式，统一处理缺值、未知参数、互斥开关与剩余位置参数；支持明确约定的 `--config-dir=<目录>` 和 `--config-dir <目录>`。`--help` / `--version` 只输出本地信息，先于实例发现和 Core 启动。不要把任意参数拼成 shell 命令或无筛选地转发给业务引擎。

`launch.go` 调用 Core 的公开 runtime，使用 `os/signal` 与 `context` 组织停止流程；无参数启动与 `serve` 不产生两套实现。帮助信息中文优先，失败使用可识别的退出码。日志输出到 stderr；需要供 Desktop 或脚本读取的维护命令以独立结构化结果输出到 stdout，不混入彩色提示与进度条。[Go signal](https://pkg.go.dev/os/signal)

`config validate` 可只读校验传入的草稿 / stdin，不获取实例锁、不连接机器人；Desktop 持锁编辑时调用此纯校验路径，避免子进程重复抢锁。后续离线迁移和配置持久化通过 Core 的公开能力完成，由唯一写入进程获取配置目录的排他锁，不能同时启动第二个机器人业务实例。

Windows / Linux 的分发资产标明 OS 与架构，如 `sbu_<version>_windows_amd64.zip`。数据库驱动、图片库是否需要 CGO 或附带动态库，要在真正选型后记录；不先承诺所有依赖都能静态单文件交付。

## 3. Desktop：ShitBotUltra-Desktop

默认使用 **C# + WinUI 3 + XAML + CommunityToolkit.Mvvm**，提供 Windows 原生界面；通过受保护的管理 API 使用现有 Go Core。Avalonia 作为需要跨平台、或 WinUI 的部署条件不适合目标环境时的备选；它使用自己的渲染引擎，不应称作 Windows 原生控件。首期只维护一套 UI 实现。[WinUI 3 官方说明](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/)、[Avalonia 官方说明](https://docs.avaloniaui.net/docs/welcome)

```text
ShitBotUltra-Desktop/
├─ src/
│  └─ ShitBotUltra.Desktop/
│     ├─ ShitBotUltra.Desktop.csproj
│     ├─ App.xaml
│     ├─ App.xaml.cs              # 依赖组装、应用生命周期
│     ├─ MainWindow.xaml
│     ├─ MainWindow.xaml.cs       # 窗口行为，不放业务规则
│     ├─ Views/                  # DashboardPage、ConfigPage、LogsPage 等

│     ├─ Models/                 # 管理 API DTO 和界面状态类型
│     ├─ Services/
│     │  ├─ CoreClient.cs        # HTTP / SSE，不含绑定业务
│     │  ├─ CoreProcessService.cs # 启动 / 附加 sbu，记录进程归属
│     │  ├─ ConfigFileService.cs # 配置原文、草稿、保存冲突
│     │  └─ UpdateService.cs   # 桌面版本提示、SHA-256 与安装状态

├─ resources/
│  └─ runtime-manifest.json      # 兼容的 CLI 版本、资产名、摘要
├─ packaging/windows/           # 发行时包含固定版本的 sbu.exe
├─ docs/
├─ .github/workflows/
├─ ShitBotUltra.Desktop.sln
```

ViewModel 使用异步命令与取消令牌处理网络、日志流和文件任务；需要更新控件的内容通过 UI 调度器切回界面线程，不同步等待网络或阻塞 UI。高频日志合并刷新并限制保留量。窗口层不自行校验 QQ 绑定策略、不执行 SQL、不连接机器人协议。

Desktop 包含经过校验的固定版本 `sbu.exe`，通过 `sbu serve --no-webui --config-dir <目录>` 在后台运行同一份 Core；首次正常运行不要求额外下载安装 Go 或 CLI。启动子进程使用 Windows 无控制台方式，参数按数组传递，不拼接 shell 命令。密钥不放命令行或日志；实例凭据通过受限文件或受保护的 IPC 传递。Desktop 的默认界面不需要 WebView；用户可另外开启 Core 的浏览器 WebUI。

.NET 与 Windows App SDK 的版本、打包 / 非打包模式、是否自包含发布和最低 Windows 版本，在发行配置中明确并锁定。安装包负责提供或安装选定模式所需的运行时；不能把“内置 CLI”误写成桌面程序必然单 EXE、无运行时依赖。如果后续选用 Avalonia，可保留服务、DTO 及适用的 ViewModel，界面与平台集成仍须迁移，不承诺直接替换 NuGet 包即可完成。

版本清单同时记录 Desktop、CLI、Core 和管理协议版本。升级 Desktop 不应悄悄替换由用户独立安装的 CLI 或系统服务。GUI 专属偏好（窗口大小、主题、最近目录）与 Core 配置分开存放。

Java 根包固定为 `shitbotteam.ultra.minecraft`。平台包依次为 `.bukkit`、`.velocity`、`.bungee`、`.nukkit`；公开 `.api` 与通信 `.bridge` 由独立 MC API 仓库提供，不在本仓库重复实现。插件描述文件里的入口全限定名与源码目录保持一致。

Maven groupId 规划为 `shitbotteam.ultra`，artifactId 按 `ultra-minecraft-api`、`ultra-minecraft-bukkit` 等区分。Java 源码包名和制品仓库坐标是不同概念：向要求命名空间验证的公共制品仓库发布前，确认坐标资格；如需调整发布坐标，单独记录映射，不擅自更改已经确定的 Java 根包。

每个平台单独输出 `ShitBotUltra-Bukkit-<version>.jar`、`ShitBotUltra-Velocity-<version>.jar` 等，不把所有平台依赖打进一个大 JAR。独立 Java 客户端负责协议与连接，平台模块负责事件、执行器、调度和 bStats。机器人实现、JDBC 驱动、业务数据库与 Chromium 不进入 JAR。

Java 目标版本按平台分别设置。普通版 Spigot / Bungee 为 Java 8、Nukkit 为 Java 17、Velocity 为 Java 21；Ultra 的最终矩阵需明确决定，不能因构建 JDK 升级而意外抬高所有 JAR 的运行要求。

## 5. 协议归属与跨仓库依赖

Core 的 `api/` 是协议唯一来源。每次发布协议，提供版本、schema、示例和变更说明；MC API 中的 Java 客户端与 Desktop 的 C# 客户端固定来源版本，不复制修改另一份契约。插件、模板与适配器契约各自版本化，不把 Bridge 协议号作为所有扩展的版本号。

- JSON Schema 描述字段形状；握手、顺序、超时、重连和副作用的语义必须写成协议文档。
- 管理 API 使用 OpenAPI；SSE 事件另外定义 schema 和恢复规则。
- 消费仓库记录 schema 版本和摘要，生成文件加来源说明，不人工修改生成代码。
- 协议升级先让 Core 兼容新旧客户端，再更新 CLI / Desktop / JAR；删除旧能力前给出明确的废弃版本。
- 运行时连接按协议主版本和 capability 协商；不以字符串比较仓库版本号判断兼容。
- 本地并排开发可使用 `go.work`；提交的 `go.mod` 不保留指向维护者电脑绝对路径的 `replace`。

## 6. 命名与中文信息

统一前缀为 **`shitbotteam.ultra`**，组件末段使用 `core`、`cli`、`desktop`、`minecraft`、`webui`。此规则落实到适用的语言命名空间或包元数据，不把 Go 模块强行写成 Java 点分包名。

| 组件 | 统一标识 / 根前缀 | 在当前语言中的落点 |
| --- | --- | --- |
| Minecraft | `shitbotteam.ultra.minecraft` | Java 根包；目录 `shitbotteam/ultra/minecraft/` |
| Desktop | `shitbotteam.ultra.desktop` | C# `RootNamespace` 与源码 namespace；WinUI 的 `x:Class` 同步使用 |
| Core | `shitbotteam.ultra.core` | 组件元数据标识；Go module 仍为 `github.com/ShitBot-Team/ShitBotUltra`，包名使用 `runtime`、`binding` 等 |
| CLI | `shitbotteam.ultra.cli` | 组件元数据标识；Go module 为 `github.com/ShitBot-Team/ShitBotUltra-CLI`，入口保留 `cmd/sbu` |
| WebUI | `shitbotteam.ultra.webui` | `package.json` 的包名；首期设为私有构建包，TypeScript 使用 ES 模块 |

C# 项目文件 / 程序集可保持产品名称 `ShitBotUltra.Desktop`，显式设置 `RootNamespace` 为 `shitbotteam.ultra.desktop`；源码和 XAML 不依赖项目名自动推导命名空间。例如 `shitbotteam.ultra.desktop.Views.ConfigPage`、`shitbotteam.ultra.desktop.ViewModels.ConfigViewModel`。组件根前缀按要求使用小写，子命名空间和类型保持 C# 习惯；即使改用 Avalonia 也沿用同一根前缀。

| 对象 | 规范与例子 |
| --- | --- |
| 产品 / 仓库 | `ShitBotUltra`、`ShitBotUltra-CLI`，品牌名称统一 |
| 可执行文件 | `sbu`，Windows 为 `sbu.exe` |
| Go 包 | 小写单词，如 `binding`、`inventory`；避免泛化的 `utils` / `common` 垃圾桶 |
| Go 标识符 | 导出 `BindingService`，内部 `resolvePlayer`，接口在消费者处定义 |
| 组件根前缀 | `shitbotteam.ultra.<组件名>`；Java、C# 与 WebUI 包元数据按上表映射 |
| C# 类型 / 方法 | `CoreClient`、`ConfigViewModel`、`LoadConfigAsync`；异步方法使用 `Async` 后缀 |
| Java 类型 / 方法 | `PlayerSnapshot`、`captureInventory`，包名全小写 |
| WebUI 组件 | `ServerList.vue`；业务文件按 feature 归组 |
| 协议字段 / 配置键 | 新协议统一 `snake_case`，如 `request_id`、`config_version` |
| 事件 / 动作 | 稳定英文点分名称，如 `player.joined`、`inventory.snapshot`、`command.execute` |
| 错误码 | 稳定大写，如 `CORE_UNAVAILABLE`、`REVISION_CONFLICT`；中文解释单独返回 |
| 文档 | 中文文件名与正文可用，源码和 API 标识符保持生态惯例 |

中文是默认用户语言，用户界面、帮助、日志说明、注释和 Issue 都可用中文。提交信息采用 Conventional Commits 的英文类型前缀，描述和正文可用中文；人工和 AI 辅助提交遵守同一规则。协议常量不能随界面语言改变。日志同时带稳定 `event` / `code` 和中文 `message`，便于搜索与国际化扩展；不把中文文本本身当作状态判断依据。

## 7. Git、版本与发布

提交信息统一采用 Conventional Commits，格式为 `type: 描述` 或 `type(scope): 描述`；英文类型前缀固定，描述与正文可用中文。类型使用 `fix`、`feat`、`refactor`、`docs`、`style`、`test`、`chore`，用途与完整规则见[贡献指南](../../CONTRIBUTING.md)。人工编写或由 AI 生成的提交信息都遵循此约定，例如：

```text
docs: 明确主程序与游戏适配器的职责边界
fix(core): 修复绑定验证码过期后仍可使用的问题
feat(desktop): 增加配置冲突提示
feat(minecraft): 适配 Folia 玩家调度器
```

按职责分批提交，使用系统 Git、实际提交者身份及现有签名配置；AI 工具不添加自身署名或 AI `Co-authored-by`。推送到 GitHub 时要求显示 `Verified`，本地签名与平台核验分别确认。新格式应用于后续提交，不要求重写已有提交历史。

欢迎 PR，包括 AI 辅助编写的代码和文档。PR 标题采用相同格式，单个 PR 聚焦一个目的，正文说明原因、改动、兼容影响及实际验证情况；没有运行测试时如实注明。提交者阅读改动并回应评审即可，不要求额外填写 AI 工具声明。完整约定统一维护在[贡献指南](../../CONTRIBUTING.md#pull-request-约定)。

Git 提交继续签名并核对 GitHub Verified。发行资产按维护者要求只提供对应文件的 SHA-256、版本 / 平台索引、依赖许可与兼容信息，不要求 `.sig`、公钥或密钥轮换。CLI、Desktop 和 WebUI 的更新提示、按钮 / 命令及多资产选择统一见[自动更新计划](03-协议配置与迁移.md#5-自动更新与发行)。

本阶段按要求不写代码，不运行测试或构建。五个仓库只维护计划与规范；后续功能验证由维护者自行安排，文档中的验收条件不能写成已通过结果。
