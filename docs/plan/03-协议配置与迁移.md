# 协议、配置与普通版迁移

所有消息结构、命令和配置片段都是设计示例，需在实现阶段固化为版本化契约。

## 1. 三条通信通道

| 通道 | 发起方 → 接收方 | 内容与边界 |
| --- | --- | --- |
| 游戏 Bridge | JAR 主动连接 Core | 双向 WebSocket：游戏事件、登录请求、状态快照、动作与响应；每节点独立凭据 |
| 机器人 | Core 的独立适配器连接平台，或接收平台回调 | 首期 OneBot v11 正向 WebSocket；QQ 官方与 Discord 使用各自协议，凭据只在 Core |
| 管理 | Desktop / WebUI / 后续 CLI 管理命令连接 Core | HTTP JSON 管理 API，SSE 推送日志和状态；启动器本身在进程内托管 Core，管理凭据不能复用节点凭据 |

默认监听本机，跨机器由管理员明确配置监听地址、可信 TLS 与访问控制。JAR 主动连接可以减少子服入站端口配置，但不意味着远程明文连接自动安全。首次配置生成独立随机 Token；配置示例中的占位值不能启动真实连接。

WebUI 默认同源访问管理 API。认证会话使用受限 Cookie 或等价机制，处理 CSRF、Origin、Host 校验及会话过期；不能把“本机访问”当成无需鉴权。浏览器登录可采用一次性入口交换会话，长期 Token 不进入 URL、前端打包文件或调试日志。

JAR 只接受与其已认证连接绑定的 `node_id`，Core 根据节点权限决定可路由的服务器和动作。传来的 payload 不得自行提升身份。用户可访问的日志和事件检查器默认脱敏 Token、QQ / 群标识及私密消息内容。

## 2. Bridge v1 契约草案

### 2.1 握手与能力

连接建立后交换：`protocol_version`、`adapter_version`、`node_id`、`network_id`、`server_id`、`platform`、`minecraft_version`、`boot_id`、`capabilities`。服务器清单中的节点身份由 Core 认证配置确认。

示例能力：`chat.send`、`player.kick`、`login.authorize`、`inventory.read`、`tps.read`、`permission.check`、`placeholder.resolve`。代理、Bukkit 和 Nukkit 的能力不同；不支持时返回 `UNSUPPORTED_CAPABILITY`，不能假装成功或用代理 TPS 代替后端 TPS。

### 2.2 消息外层

```json
{
  "protocol_version": 1,
  "kind": "event",
  "type": "player.joined",
  "message_id": "01-example-unique-id",
  "request_id": null,
  "node_id": "lobby-01",
  "boot_id": "boot-example",
  "sequence": 42,
  "occurred_at": "2026-11-08T10:00:00Z",
  "payload": {
    "player_id": "uuid-from-authenticated-platform",
    "player_name": "Steve"
  }
}
```

ID、QQ / 群号和 UUID 一律字符串，避免 JavaScript 数字精度或基岩名称问题；序号约定在 JSON 安全整数范围内，长连接达到上限前更新会话。时间统一 UTC；显示时再转本地时区。`sequence` 只在指定 `node_id + boot_id` 内有顺序含义，不能跨节点比较成全局顺序。

`kind` 区分 `event`、`request`、`response`、`control`。响应带原 `request_id`、成功数据或稳定错误码；有副作用的请求另带 `idempotency_key`，并携带可校验的有效期。超时执行不得仅依赖两台主机墙钟完全同步；接收端使用协商的时钟偏差范围和本地单调时钟预算，拒绝明显过期请求。

### 2.3 可靠性与反压

- 心跳、指数退避和随机抖动用于重连；队列大小、消息大小、解压上限和并发请求数都要有配置上限。
- 事件先复制成不可变 DTO，再离开游戏线程序列化、压缩和发送；不传 Bukkit 对象、任意 Java 序列化对象或整个 NBT 对象图。
- 状态快照可以合并为最新值；普通聊天只做有限短时缓存，过期丢弃并计数；登录授权不进入离线重放队列。
- 需要恢复的事件使用有限重放窗口、确认游标和 `message_id` 去重。Core 持久化关键消费状态；重启或窗口过期后请求全量状态对账。不要把所有事件描述为无条件“恰好一次”。
- 有副作用的动作由 JAR 在有限窗口内保存请求记录，重复请求返回已有状态。JAR 重启且无法确认结果时返回未知状态，不尝试补做。
- 命令可能已经执行但响应丢失：Core 标为“执行结果未知”，不自动重发。业务数据库事务与游戏命令无法组成原子事务，持久化幂等键也不能消除所有崩溃窗口。
- 大图、资源包走有限大小的资源接口 / 文件上传流程，Bridge 传资源标识、摘要和元数据；避免把大量 Base64 塞进聊天事件队列。

### 2.4 登录、权限与平台线程

绑定门禁启用时，JAR 发起 `login.authorize`，Core 完成验证码 / 白名单规则判断并返回结果。请求使用鉴权后可靠的用户名与 UUID，并记录是否处于在线认证、受信代理转发或离线身份模式；离线模式不能把名字宣称为已验证的账号所有权。

**默认建议：Core 断连或授权超时，拒绝新的受控登录，提示稍后重试；已经在线的玩家不因 Core 断线一律被踢。** 门禁本就关闭的服务器继续按自身规则登录。以后若允许离线缓存授权，必须由服主显式开启并设置 TTL，说明撤销无法实时生效；不得无限使用旧白名单。

Bukkit 使用合适的异步登录事件，Bungee 使用异步 intent，Velocity 使用带 continuation 的登录事件。不能在 Bukkit / Folia 主线程 `.get()` 网络 Future；Folia 的玩家操作必须回对应实体 / 区域线程。普通版已经有这些差异，迁移时需要保留。

快捷命令仍采用 Core 中的允许模板、绑定要求、群身份权限、参数约束和指定目标。JAR 执行经过认证的动作，保留本地可执行能力及限制；Core 请求不能隐式变成任意系统 shell。需要 LuckPerms / Vault 或在线玩家权限的查询由对应后端执行。

### 2.5 代理多服

同一网络明确唯一的总体玩家会话来源：有代理时由代理权威上报网络加入 / 退出，后端负责子服位置、背包、TPS 和 PAPI；单服时由该服负责全局会话。

后端切换不重复计算总在线时长，不重复发进退服通知。每次重连通过 `boot_id` 与完整在线快照对账，不能只按补发 join / quit 推断状态。群 ↔ 服务器映射由 Core 管理，JAR 不存 QQ 群路由表。

## 3. 配置文件与桌面直接管理

### 3.1 统一配置目录

显式 `--config-dir` 优先；Desktop 选定目录后把同一绝对路径交给 CLI。默认可采用 Windows 用户目录和 Linux XDG 路径；服务账号部署使用显式目录，不猜当前工作目录。便携模式由用户明确选择。直接运行 CLI 时首次创建默认配置，新配置开启本机 WebUI；已有配置保留原设置，缺少机器人 / 节点参数时仅启动管理入口并提示待配置。Desktop 自行启动宿主时传入 `--no-webui`，需要时再通过管理 API 开启页面服务。

```text
<配置目录>/
├─ config.yaml                   # Core 主配置，含 config_version
├─ connections.yaml              # 机器人和节点连接配置，凭据使用引用
├─ routes.yaml                   # 群与服务器路由
├─ commands.yaml                 # 快捷命令与权限规则
├─ secrets/                      # 受限访问的凭据；不纳入 Git
├─ lang/zh_CN.yaml
├─ templates/                    # Chromium 图片模板、草稿及发布快照
├─ plugins/                      # 用户本地导入的插件包；配置和数据隔离
├─ imports/                      # 用户上传的导入暂存文件和任务报告
├─ resources/                    # 显式导入的字体、材质与图标
├─ data/                         # 由 Core 独占的数据库与业务数据
├─ cache/
├─ logs/
├─ backups/
└─ run/                          # 实例锁、API 发现与受限状态文件
```

Windows 限制到当前用户 / 服务账号的 ACL，Linux 使用相应文件权限；认证凭据不混入可公开分享的配置导出。SQLite 文件不是 Desktop 的配置文件，Desktop 不直接读写业务数据库。

### 3.2 在线与离线编辑

Desktop 必须支持“打开配置目录”“打开配置原文”“保存并应用”，不要求用户通过浏览器修改。

- **Core 在线**：Desktop 通过已授权管理 API 读取原文与 revision；本机且具备文件权限时，也可直接打开配置文件。保存时携带读取时的 revision / 文件摘要，交 Core 完成校验、备份和写入。WebUI、CLI 走同样的写入入口。附加其他账号的系统服务或远程 Core 时不假设拥有其文件权限；API 单独检查配置读写权限，不能接受任意服务端文件路径。
- **Core 离线**：Desktop 在取得相同目录锁后直接编辑文件；可把草稿传给 CLI 的只读校验命令，由 Core 公开能力校验，避免 C# 维护第二套规则。此校验子进程不再获取实例锁，真正保存仍由唯一持锁进程完成。保存不会顺便启动机器人连接。
- **外部编辑器修改**：文件检测只提示变化；Core 重新校验后才应用，保留旧运行快照直到新配置就绪。未保存的 UI 草稿遇 revision 变化应提示冲突，禁止静默覆盖。
- **持久化**：同目录临时文件加原子替换与备份；多文件变更使用事务清单 / 恢复标记，不把逐个 rename 说成跨文件原子事务。
- **生效**：先校验和准备依赖，再持久化并切换运行快照；连接类配置失败时明确保留旧连接或返回未生效状态。无法热切换的项目显示“待重启”，不能保存即宣称生效。

环境变量用于秘密注入，CLI flag 用于本次运行覆盖；优先级建议 `默认值 < 文件 < 环境变量 < 显式 flag`。界面显示有效值的来源，环境变量 / flag 的覆盖不自动写回文件。[Caddy 的 ETag / If-Match 配置并发设计](https://caddyserver.com/docs/api#concurrent-config-changes)可作为冲突检测参考。

`--webui` / `--no-webui` 专门定义为 WebUI 页面服务的**启动初始状态**，不锁死运行期间的开关。Desktop 的“开启 WebUI”通过受权管理 API 修改当前会话状态；是否保存为下次默认值由配置保存操作决定。程序重启仍按上述启动优先级计算，管理 API 始终独立于页面服务开关运行。

### 3.3 JAR 的最小配置示意

```yaml
config_version: 1
core:
  url: "ws://127.0.0.1:<实际端口>/bridge/v1"
  token_file: "core-token.txt"
node:
  id: "lobby-01"
  network_id: "main"
  server_id: "lobby"
login:
  core_unavailable: "deny_new_logins"
bstats:
  enabled: false
```

这是不可直接运行的占位示例。远程连接使用 `wss://`；统计开关在正式 ID 接入前保持关闭。JAR 不包含 OneBot Token、QQ 群规则、数据库密码或渲染配置。重连、队列等使用合理内置默认值，只有必要时暴露高级选项。

| `config-templates/`、`lang/` | 多语言、可配置提示、模板默认值、版本迁移 | Core 配置和语言资源；JAR 仅保留必要本地提示 |

### 4.1 数据导入规则

普通版当前 schema 为 7，涉及 `shitbot_bindings`、`shitbot_bind_codes`、`shitbot_bind_attempts`、`shitbot_inventory_snapshots`、`shitbot_player_stats`。Ultra 设计自己的 schema 和迁移版本，不原地接管普通版旧库。

1. 先让维护者停止旧业务入口，并取得一致的数据库备份 / 导出；不能对正在写入的 SQLite 只复制主文件忽略 WAL。
2. 导入器默认只读源副本，先生成 dry-run 报告，列出记录数、冲突、未知 schema、跳过项和目标路径。
3. 保留玩家名大小写、可选 UUID、无 QQ 白名单、QQ 字符串、时间戳与累计时长。基岩版名字可能有空格，不能套 Java 玩家名规则或统一小写。
4. 验证码与尝试次数作为一组临时状态处理：建议旧验证码全部失效，启用迁移后的短期绑定节流，再重新签发；报告明确写出变化，不能无说明清空限制。
5. 背包 codec 要识别旧格式 1 / 2 / 3；现有上限为压缩 512 KiB、解压 2 MiB，导入阶段保留等价限制，未知或损坏格式隔离报告。
6. 资源包、Mod 图标、玩家头纹理、旧 data value 和新 CustomModelData 语义逐项映射；Core 运行在另一台机器时要求显式导入资源，不默认扫描插件旁边的全部 JAR 或上传整服文件。
7. 新库独立保存；二次导入利用源标识和迁移记录避免重复。成功后输出摘要，保留原库和配置副本，方便维护者退回普通版。
8. 切换时避免普通版和 Ultra 同时连接同一机器人、响应同一群指令。回退不会自动把 Ultra 运行期间的新数据写回普通版，需单独导出 / 协调。

EasyBot 旧数据导入保留为另一种显式导入器，不与 ShitBot 导入规则混在一起。

白名单专用导入同时支持单文件与多文件合并，只处理绑定 / 无 QQ 白名单。合并、冲突、预览过期、事务及重复导入规则见[白名单导入计划](06-扩展接口与数据导入.md#5-shitbot-白名单的单文件与批量合并导入)，不要把一次白名单导入扩大成全库迁移。

### 4.2 图片与 Java API 的迁移难点

原版图片依赖 Java2D，Ultra 的默认路线现确定为 **Core 托管 Headless Chromium 渲染 HTML/CSS/JavaScript**。在线 / 个人 / 背包图片使用统一数据上下文和渲染接口；模板可本地导入、配置主题 / CSS、预览、发布和回滚。旧模板不能直接执行，转换时报告不支持项，不承诺布局完全相同。

浏览器进程、固定版本资源、有限队列、超时与失败降级都在主程序侧，Minecraft JAR 不携带渲染器。参考 EasyBot 的浏览器模板方式，并规划适配 BaiZhouziYou 的三个模板，保留作者、项目链接及上游声明；[详细接口与署名要求](06-扩展接口与数据导入.md#4-内置-chromium-图片模板能力)为准。

Java 公共 API 和通信客户端归独立 [ShitBotUltra-MC-API](https://github.com/ShitBot-Team/ShitBotUltra-MC-API)，Minecraft 平台模块只调用依赖。异步 Future 具有远程语义：离线、超时、取消和结果未知均明确返回；回调不保证游戏线程。同步 PAPI 只读有期限的本地缓存，Core → 游戏数据提供器调用带 deadline，由平台切回正确调度器。[独立 Java API 计划](06-扩展接口与数据导入.md#6-独立-java-mc-api)

## 5. 自动更新与发行

更新来源默认使用各组件在 `ShitBot-Team` 下的官方 GitHub Releases，不要求维护者另建更新服务。CLI、Desktop、WebUI 都提示当前与可用版本，并提供主动检查和升级入口。维护者已明确：**只核对 SHA-256，不设计发行包 sig、公钥或密钥轮换**；Git commit 的签名和 GitHub Verified 仍按贡献规范执行。

### 5.1 各入口的交互

| 入口 | 版本提示与检查 | 升级方式 |
| --- | --- | --- |
| CLI | 启动后异步检查并在终端提示；拟定 `sbu update check` 手动检查 | `sbu update` 选择当前平台资产，显示版本与进度，校验后退出替换并重启；无人值守模式使用明确配置 / 参数 |
| Desktop | 状态页 / 关于页显示更新提示、“检查更新”和“升级”按钮 | 下载对应桌面安装资产，核对 SHA-256，保存状态后交安装 / 替换流程；随包 CLI 与 Core 版本同步记录 |
| WebUI | 页面提示 Core / 宿主版本、新版本与更新日志，提供检查与升级按钮 | 经授权管理 API 请求拥有当前进程的宿主执行升级，显示进度与重连状态；页面静态资源随 Core 一起更新 |

默认可在启动后和可配置间隔异步检查，检查失败不影响正常运行；支持关闭检查和选择稳定 / 预发行通道。自动检查与无人值守安装分别配置：用户点击升级后自动完成下载、校验和安装；需要定时自动安装时由用户启用并配置维护窗口。所有入口共享更新任务状态，重复点击不建立多个安装任务。

### 5.2 Release 文件较多时如何选择

默认从 GitHub Releases API 的资产列表取得文件名、大小、下载地址及对应 `digest` 中的 SHA-256，按固定命名约定匹配组件、OS、架构和安装方式。摘要缺失时可读取同 release 的一份 `SHA256SUMS`；资产类型复杂时再增加轻量索引，统一列文件映射与兼容范围。不为每个文件增加 sig，也不要求每个 release 另建更新服务。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)

- 根据当前组件、OS、架构和安装方式匹配唯一资产；不把 release 第一个文件当安装包，不下载全部资产再逐个计算。
- SHA-256 必须对应完整文件名。排除源码压缩包、其他平台、调试文件及不匹配的安装格式；没有唯一匹配项或摘要时提示无法自动升级并提供对应 release 页面。
- 使用 HTTPS 下载临时文件，检查大小和该文件的 SHA-256；匹配后才进入安装。失败删除临时下载并保留现有程序；不增加 `.sig` 或公钥文件要求。
- Core 作为 Go module 随 CLI 构建，不单独替换运行中的 Go 库；WebUI 随 Core 交付。Java API 通过开发者更新依赖版本升级，不作为运行中自更新组件。

### 5.3 安装、归属与恢复

各仓库独立版本，更新前检查 Bridge / 管理 API / Java API 兼容范围，显示影响与备份位置。Desktop 只更新自己管理的桌面包和随包宿主；附加独立 CLI、系统服务或远程 Core 时，通过对应宿主支持的受权更新入口操作，不静默替换其他安装。

Windows 正在运行的 EXE 由退出后的更新 helper 或安装器替换，Linux 按受支持的安装方式切换；保持配置目录、用户插件和模板数据。安装权限不足或宿主不支持时返回清楚的状态和下载入口。CLI / Core 更新完成后重启宿主，WebUI 显示断开与重新连接；Core 升级不强制重启 Minecraft。

Minecraft JAR 仅提供版本与兼容提示，按平台维护流程替换并正常重启，不做热卸载。更新前备份受影响数据，程序替换失败保留 / 恢复旧版本；若 schema 已升级，回退必须使用兼容的数据备份，不能只恢复 EXE。升级成功、失败或仍待重启分别显示，不能下载完成就宣称已经升级。
