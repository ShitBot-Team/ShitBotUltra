## 1. 已确定的范围

| 维护者要求 | 计划落点 |
| --- | --- |
| 不建设插件市场，允许自己写插件和自定义导入 | Core 插件接口、版本化 SDK、本地目录 / ZIP 导入与启停管理 |
| 适配器单独编写，能够扩展到不同平台 | 独立适配器包、公开契约与注册机制；首发 OneBot v11，后续 QQ 官方机器人与 Discord |
| 图片像普通版一样可自定义，采用 Chrome 内核 | Core 内置模板管理能力，托管 Headless Chromium，开放数据与渲染接口 |
| 可内置参考模板并带作者、项目地址 | 规划适配 BaiZhouziYou 的三个模板，保留来源、许可、修改记录与第三方声明 |
| 批量导入 ShitBot 数据库白名单，能合并也能单独导入文件 | 一个导入服务处理单文件、多文件合并、冲突预览与导入记录 |
| Java 端提供单独依赖，集中与主程序对接的方法 | 独立 `ShitBotUltra-MC-API` 仓库；Minecraft 平台模块依赖 API / 客户端 |
| 补齐 LICENSE | 五仓库各自提供 AGPL-3.0-only 正文，模板等第三方内容另保留原许可 |

以下接口划分是本计划的建议实现，不等于已经交付 SDK、插件运行环境或第三方兼容能力。

## 2. 插件接口与本地导入

### 2.1 插件能做什么

Core 负责统一的插件宿主，插件只通过公开服务操作业务。普通功能扩展、机器人适配器、图片模板分别管理，不能因为都有 `manifest` 就混用加载器。

| 接口范围 | 拟提供能力 | 边界 |
| --- | --- | --- |
| 生命周期 | 初始化、启用、停用、释放，查询运行状态与错误 | 停用后注销订阅、定时任务和资源；异常不能终止 Core |
| 事件 | 订阅标准消息、绑定、游戏状态等事件 | 使用统一 DTO、订阅范围及有界队列，不把原始平台对象暴露给插件 |
| 命令与消息 | 注册命令处理器，向授权会话发送统一消息 | 沿用 Core 的权限、冷却、路由与适配器能力判断 |
| 业务访问 | 查询或按授权修改绑定、白名单、玩家资料 | 调用业务服务，不直接访问业务数据库 |
| 游戏访问 | 查询快照、占位符，发起允许的游戏动作 | 走 Bridge 的节点权限、deadline 与幂等规则 |
| 图片 | 注册数据提供器、请求指定模板渲染 | 走统一图片接口，不自行启动无管理的浏览器 |
| 配置与存储 | 声明配置项，读写本插件命名空间的数据 | 不共享插件内部表，不提供任意 SQL 接口 |
| 诊断 | 带插件标识的日志、健康状态与错误 | 凭据及私密数据沿用 Core 脱敏规则 |

SDK 契约在 Core 的 `api/extensions/v1/` 维护，声明 API 版本、数据结构、错误码和生命周期。建议普通脚本插件使用 JavaScript，TypeScript 编译成 JavaScript 后导入；具体执行引擎在实施阶段固定。运行时由 Core 托管独立 worker 与受控宿主接口，不默认要求最终用户安装 Node.js，不使用 Go 原生动态插件作为通用导入格式。

本地可执行插件按管理员信任的扩展处理。接口权限约束宿主调用，worker 隔离用于管理生命周期与故障，不把它描述成完整的操作系统安全沙箱。

### 2.2 导入与版本管理

- 接受用户选择的插件目录或单插件 ZIP，不连接市场、不自动发现远程插件、不自动安装依赖。
- 清单至少包含稳定 `id`、名称、版本、作者、项目地址、许可证、入口、SDK 兼容范围、申请能力及配置 schema。
- 导入先检查包结构、清单、兼容范围和资源限制；ZIP 拒绝越界路径与不受支持的链接，限制解压大小。显示作者、来源、权限与状态，用户启用后才执行。
- 安装文件、插件配置、插件数据分别存放。同 ID 的新版本按显式升级处理，不依赖文件覆盖触发自动执行；升级保留旧版本以便回退。
- 首期支持安装、启用、停用、查看错误和移除。热替换只有在停止、资源释放及兼容语义明确后再做，不承诺任意插件无损热重载。
- WebUI / Desktop 通过同一管理 API 管理插件；CLI 只托管 Core 并显示错误，不建立第二套加载器。

## 3. 可扩展机器人适配器

### 3.1 独立实现与公共契约

业务层依赖平台中立的消息、身份、会话与能力接口。首期每个内置协议使用单独 Go 包：`internal/adapter/onebotv11/`、后续 `qqofficial/`、`discord/`，由组合入口注册，不在绑定、白名单和消息路由中分支判断 OneBot 原始字段。

公开 Go 适配器开发面建议放在 `sdk/adapter/`，供自定义实现编译注册；参数与返回值不引用 `internal` 类型。具体连接协议、鉴权方式、事件解码及平台限流由各适配器负责。首期不要求动态加载 Go 二进制；通过插件扩展适配器时，复用同一版本化事件与动作契约。

| 适配器契约 | 职责 |
| --- | --- |
| 描述与配置 schema | 协议类型、版本、账号作用域、配置项和支持的能力 |
| 工厂与注册 | 以协议类型注册构造器；新增适配器不改业务模块 |
| 启动 / 停止 / 状态 | 生命周期、认证、会话、重连、最后错误与健康状态 |
| 事件入口 | 将平台事件转换成统一事件，保留原消息 ID、来源与关联信息 |
| 消息发送 | 接受统一消息段与目标，返回平台消息标识或稳定错误 |
| 可选动作 | 成员信息、撤回、会话管理等按 capability 提供，不强制所有平台实现 |

适配器可以有长连接，也可以有回调 HTTP 或请求接口。Core 不强制所有平台模拟 OneBot WebSocket；回调注册和验签属于对应平台协议的接入职责，与发行包不做 sig 的约定无关。

### 3.2 身份与消息模型

- 身份至少包含平台、账号 / 应用作用域和不透明字符串 ID；连接实例另有 `connection_id`。显示名称与身份分开存放。
- QQ 官方的 openid、频道成员 ID、OneBot 的 QQ 号、Discord 用户 ID 不能按数字相同自动合并。跨平台绑定必须经过业务确认流程。
- 会话包含类型与作用域，覆盖私聊、群、服务器 / 频道及未来线程，路由不只使用 `group_id`。
- 消息采用文本、图片、提及、引用、附件等结构化消息段。保留平台扩展信息，但普通业务不依赖它；不支持的段按明确策略降级或返回错误。
- 接收去重至少结合连接与平台事件 / 消息 ID。发送遵守平台限流和有效回复条件；副作用结果未知时不盲目重发。
- 权限、提及规则、主动发送、图片上传等能力按平台和会话公开，界面据此解释不可用原因，不把 OneBot 的管理员权限直接套到所有平台。

### 3.3 对接顺序

| 适配器 | 实施计划 | 依据 |
| --- | --- | --- |
| OneBot v11 | 首发正向 WebSocket，优先接入 SnowLuma；其余传输按需要增加 | [OneBot 11 标准](https://github.com/botuniverse/onebot-11) |
| QQ 官方机器人 | 独立应用配置、访问凭证与事件接入，群 / 私聊 / 频道按实际授权能力支持 | [官方接入文档](https://bot.q.qq.com/wiki/develop/api-v2/) |
| Discord | 保留独立适配器与能力扩展路径，在对应实施任务中固定事件和命令范围 | [开发文档](https://docs.discord.com/developers/intro) |

首期可用范围仍以实现后的兼容记录为准；以上对接目标不表示已经取得平台资质或完成联调。

## 4. 内置 Chromium 图片模板能力

### 4.1 渲染与开发接口

采用 **HTML / CSS / JavaScript + Headless Chromium** 作为默认图片模板路线，由 Go Core 管理浏览器进程与有界渲染队列。控制层通过 Chrome DevTools Protocol 截图，实施时固定 Go 控制库与浏览器版本；不再把 Go 原生绘图或 Java2D worker 作为待定的默认方案。[Headless Chrome](https://developer.chrome.com/docs/automation-and-testing/headless)、[CDP](https://chromedevtools.github.io/devtools-protocol/)

模板开发可使用原生前端、Vue、React 等，但导入的是构建完成的本地静态资源。普通运行无需安装前端构建工具。Core 内置的是模板宿主和管理能力；完整发行包提供固定浏览器资源，另可配置已安装的受支持浏览器路径。具体 OS / 架构及浏览器分发许可在实施时登记，不能把 Chromium 写成 Go 单文件内的零依赖组件。

| 接口 | 拟定输入与结果 |
| --- | --- |
| 模板清单 | ID、版本、入口、作者、项目地址、许可、数据参数、尺寸、输出格式及引擎兼容范围 |
| 数据上下文 | 玩家 / 在线 / 性能等不可变快照、受限资源 URL、主题、语言和配置参数 |
| 渲染请求 | 模板版本、上下文、宽高、像素倍率、格式与 deadline；返回图片资源标识和元数据 |
| 就绪通知 | 页面、字体、图片加载后由 SDK 显式通知可截图；Load / NetworkIdle 作为辅助等待条件，均有超时 |
| 数据提供器 | 通过 Core 注册和解析模板所需业务数据；游戏查询通过 Java API / Bridge 批量获取 |
| 管理能力 | 本地导入、预览、草稿、发布快照、主题 / CSS 配置、回滚与恢复内置模板 |

浏览器只收到渲染需要的数据，不注入管理 Token、数据库凭据或任意文件访问接口。模板资源限于本包及授权资源，外部资源由明确策略控制；页面 SDK 不直接开放任意服务器命令。任务使用独立页面 / 上下文、像素与资源上限、取消和超时，浏览器失败可以重启并将消息降级为文字。

图片模式与自定义范围覆盖普通版的在线图、个人资料、背包及后续高级模板。旧 Java2D 模板不能直接运行；保留导入映射说明并报告不支持项，不承诺完全相同的布局或字体效果。

### 4.2 参考模板与署名

参考 [EasyBot 图片模板开发说明](https://docs.inectar.cn/docs/easybot/dev/image_template/) 的浏览器模板思路；Ultra 自行定义清单和 SDK，不要求复制 EasyBot 的框架结构，也不声明它的 SDK 可直接运行。

计划适配并内置以下 [EasyBot Image Templates](https://github.com/BaizhouziYou/easybot-image-templates) 模板：服务器在线列表、玩家统计资料卡、服务器性能监控。作者署名为 **BaiZhouziYou**，项目地址保留为 `https://github.com/BaizhouziYou/easybot-image-templates`。适配工作是后续代码阶段任务，本次没有复制模板或媒体素材。

实际引入时记录上游固定 commit / 版本、修改内容和日期，将作者、项目名、源码链接显示在模板详情与关于 / 致谢页，并随包保留上游 `LICENSE`、`NOTICE.md`、附加条款和第三方声明。上游说明不要求每张输出图加水印；字体、库、封面和预览素材分别按各自授权处理。具体文件入口见[许可说明](../licensing.md#第三方模板与浏览器资源)。

## 5. ShitBot 白名单的单文件与批量合并导入

### 5.1 同一服务支持两种入口

- **单文件**：选择一个 ShitBot SQLite 一致性副本，或后续由 Ultra 明确定义的白名单导出文件；预览后只导入该文件的数据。
- **批量合并**：显式选择多个文件，为各文件指定来源和目标服务器 / 网络，先汇总、去重并分析源文件之间以及与目标库之间的冲突，再作为同一个导入任务写入。
- 两种入口共享格式识别、字段映射、策略、报告和写入服务，WebUI / Desktop 走管理 API，CLI 后续维护命令复用它；不扫描整台机器寻找数据库。

首期识别 ShitBot 的 SQLite 格式与受支持 schema；MySQL 导入通过明确的只读导出 / 导入器扩展，不把任意 SQL 文件直接执行进 Core。白名单任务默认只迁移绑定与白名单，不顺带导入验证码、背包、玩家统计或配置。全量迁移仍按[普通版迁移规则](03-协议配置与迁移.md#41-数据导入规则)单独处理。

### 5.2 保留数据语义与冲突策略

普通版 `shitbot_bindings` 同时存储 QQ 绑定和无 QQ 白名单：`qq_id` 为空的记录不能丢弃。保留玩家名大小写及空格、可选 UUID、时间戳和来源；不能给原本无 QQ 的记录编造账号。

旧 QQ 号以明确的 QQ 数字身份类型保存，不冒充 QQ 官方机器人 openid。UUID 优先用于可信且相同身份模式下的匹配；没有 UUID 时采用与目标服务器一致的玩家身份规则，无法判定的大小写、基岩或离线身份差异列为冲突。

| 情况 | 默认行为 | 用户可选处理 |
| --- | --- | --- |
| 完全相同的重复项 | 合并为一项，报告各来源 | 保留来源记录 |
| 新玩家，目标库无记录 | 准备新增 | 排除本条 |
| 同一玩家对应不同 QQ / 身份 | 保留目标记录并列为冲突 | 在预览中明确选择来源或跳过 |
| 同 UUID 不同名字或身份模式不一致 | 报告冲突，不按文件顺序覆盖 | 确认映射或排除 |
| 无 QQ 白名单与已有绑定相遇 | 保留有效绑定，不降级成无 QQ | 按条明确调整 |
| 合并后超过绑定数量上限 | 阻止冲突项提交，展示数量 | 排除部分记录或先调整业务配置 |
| 未知 schema、坏文件、无效数据 | 标明文件与记录，默认阻止该批执行 | 用户排除问题来源后重新预览 |

“合并”表示来源集合的去重与冲突处理，不表示允许覆盖所有现有记录。预览清楚列出新增、重复、保留、冲突、排除及失败数量，敏感账号按管理权限显示。

### 5.3 写入、重复导入与恢复

1. 源文件始终只读；维护者先停止旧写入或获取一致性备份，SQLite 不只复制仍有活动 WAL 的主文件。
2. 预览绑定文件摘要、目标数据 revision、目标范围与冲突选择；任一变化要求重新预览，不能把过时报告直接执行。
3. 执行前备份目标数据，默认以一个任务事务提交全部已选有效记录；失败回滚，不悄悄成功一半。大批量使用 staging 与分段读取，不绕过整批提交语义。
4. 用导入任务、源文件摘要和业务唯一键记录来源；重复执行不重复新增。导入不触发入群欢迎、踢人、验证码或外部命令。
5. 输出可下载报告及备份位置。恢复只撤销该任务且尚未被后续业务修改的数据；有后续修改时报告冲突，不盲目覆盖整个运行库。

## 6. 独立 Java MC API

仓库：[ShitBot-Team/ShitBotUltra-MC-API](https://github.com/ShitBot-Team/ShitBotUltra-MC-API)。本次只初始化计划、代理入口和 AGPL-3.0-only `LICENSE`，Java 类与 Maven 工程留待后续授权。

### 6.1 依赖方向

`Minecraft 平台模块 → MC API / Java 客户端 → Core Bridge`。API 及客户端放在独立 MC API 仓库，Minecraft 仓库不再维护一份 `bridge-api` / `bridge-common` 的通信实现。Core 的 `api/bridge/` 始终是协议唯一来源；Java 仓库记录协议版本与摘要。

建议分成纯 Java 公共 API 与通信客户端两个 Maven 模块：前者包含 DTO、异步服务接口和能力模型，后者集中认证、握手、连接、重连、有界队列、请求关联、超时、取消、事件订阅与幂等记录。根包维持 `shitbotteam.ultra.minecraft.api`，客户端使用 `shitbotteam.ultra.minecraft.bridge`；平台依赖不得进入这两个模块。

### 6.2 对接主程序的方法集中提供

| Java 服务范围 | 对接能力 |
| --- | --- |
| 会话与能力 | 连接、状态、协议协商、节点注册、关闭与能力查询 |
| 游戏上报 | 登录请求、玩家进退、聊天、状态和背包快照 |
| 业务访问 | 查询绑定与白名单、发起授权业务请求，权限由 Core 校验 |
| 事件与动作 | 订阅 Core 事件，注册允许的游戏动作和数据提供器，回传结果 |
| 消息与图片 | 调用统一消息 / 图片接口，接收资源标识，不绑定 OneBot 字段 |
| 诊断 | 稳定错误码、请求关联、deadline、连接状态与取消 |

远程方法统一返回 `CompletionStage` / `CompletableFuture` 等异步结果，明确离线、超时、取消、不支持和结果未知。网络回调不保证处于游戏线程；平台模块负责切回 Bukkit / Folia 等正确调度器。同步 PAPI 回调只读取有期限的缓存。

Minecraft 插件以一个受管理客户端连接 Core，第三方插件依赖公共 API 并复用已提供的服务，不因每个调用者重复建连接。公共 API 避免被各插件打包成互不兼容的多份类；客户端实现是否重定位、服务如何发布由具体平台集成说明固定。

建议 Maven groupId 为 `shitbotteam.ultra`，制品区分 `ultra-minecraft-api` 与 `ultra-minecraft-client`。实际 Maven 发布地址、命名空间资格、Java 目标版本、版本兼容表及最小调用示例在实施时补充，不编造可用依赖版本。Minecraft 平台 JAR 仍各自独立发布。
