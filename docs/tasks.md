# 定时任务

本模块用于 Core 自身的定时消息与游戏动作，与本地插件的 tick 回调分别管理。配置在 `config.yaml` 的 `tasks` 数组，默认 `[]`；保存后重启宿主生效。分阶段补丁中，0005 提供配置、时点计算与数据库迁移，0006 接入执行与管理 API，0007 提供管理页面。

## 配置

每个任务只执行一个目标上的一个动作，不展开变量或调用宿主 Shell。最多 128 个任务，ID 不重复。禁用任务仍校验引用，防止启用时才发现配置失效。

```yaml
tasks:
  - id: daily-notice
    name: 每日晚间提醒
    enabled: false
    schedule:
      kind: daily
      at: '20:00'
      timezone: Asia/Shanghai
    action:
      kind: bot.message
      route_id: main-group
      text: 欢迎来到服务器，请遵守群规。
  - id: game-notice
    name: 游戏内定时广播
    enabled: false
    schedule:
      kind: interval
      every_seconds: 3600
    action:
      kind: chat.send
      node_id: survival
      text: 输入帮助命令查看服务器玩法。
```

示例引用 [examples/config.yaml](../examples/config.yaml) 中的路由与节点。启用 `bot.message` 要求该路由的连接也已启用；它是显式任务，不受路由的聊天转发或进退服通知开关控制。`chat.send` / `command.execute` 要求节点允许同名动作，执行时还会检查在线能力。命令正文不带开头 `/`，不会通过操作系统执行。

正文为 1–2000 个 UTF-8 字节，禁止控制字符（包括换行）；中文通常每字 3 字节。名称最多 128 字节。任务表单通过 `PATCH /api/v1/config/sections` 修改 `tasks`，与配置原文共享 ETag，可一次性同时修改节点或路由及其任务引用。

## 时间语义

- `interval`：60–604800 秒，以 Unix epoch 为固定基准对齐，重启不会重新计时；例如 3600 秒对应 UTC 整点。
- `daily`：显式 `HH:MM` 与 IANA 时区，不接受依赖宿主的 `Local`。Core 嵌入时区数据，不要求 Windows 或精简系统安装 zoneinfo。
- 首次启动只安排当前时间之后的时点，不补发停机期间的任务。夏令时跳过的本地时刻不执行；重复的本地时刻最多尝试一次，重启后仍由持久化日期槽去重。
- 同一任务的定时时点有持久化高水位；系统时钟回拨不会重放已尝试的时点。任务移除后保留高水位，复用 ID 不会清空它。

## 调度与执行记录

调度器使用 4 个 worker 和最多 64 条待执行队列。同一任务最多有一次排队或运行中的动作；遇到重叠、队列满、超过计划时点 30 秒仍未开始发送时，记录为 `skipped`，不积压或重试。一次执行最多占用 30 秒，Bridge / 适配器还遵守各自更短的请求期限。新周期是新的执行机会，并不是上次失败的重试。

记录写入成功后才排队，记录 `running` 后才发送。Core 重启时将遗留 `queued` 标为 `canceled`、遗留 `running` 标为 `unknown`，不重新执行。关闭时取消未发送任务并等待已派发工作退出。数据库写入失败会暂停接收新任务，需要检查存储并重启；已进入发送阶段的动作无法撤销。

`succeeded` 表示目标返回成功响应，不保证游戏命令的业务效果。断连、超时或无法确认的结果标为 `unknown`；必须先核实游戏端 / 群聊，禁止据此自动重发。一个定时时点最多尝试一次，不承诺外部系统恰好执行一次。

执行记录不保存消息 / 命令正文或远端错误原文，只保留任务名称、动作种类、目标、配置摘要、时间、状态和受限错误码。保留最多 30 天；超过最近 10000 条的已完成旧记录会清理，但保留活动任务和最近 10 分钟的记录。任务游标独立保留，不随日志清理。

## 管理 API

以下端点沿用管理 Bearer、Host / Origin 校验。完整 schema 见 [OpenAPI](../api/admin/v1/openapi.yaml)。

| 端点 | 用途 |
| --- | --- |
| `GET /api/v1/tasks` | 正在运行的任务配置、下次时点、排队 / 运行状态、暂停原因和运行配置 `revision` |
| `POST /api/v1/tasks/{id}/run` | 手动执行一次；不会移动下一次定时时点 |
| `GET /api/v1/task-runs?task_id=...&limit=100&offset=0` | 查询记录；可查已经删除的任务，按创建时间降序 |
| `GET /api/v1/task-runs/{id}` | 查询一次请求的结果，不触发动作 |

手动执行的 JSON 为 `{ "request_id": "<Unix毫秒>-<16随机字节的小写hex>", "revision": "<GET /tasks的revision>" }`。请求 ID 同时是执行记录 ID；重复提交相同 ID 只返回已有记录，不再执行。新 ID 的时间戳最多落后 5 分钟或超前 30 秒；已过期且查不到记录的 ID 会拒绝，防止日志清理后重新执行旧请求。每个任务的手动提交间隔至少 10 秒。手动请求时间戳另有持久化高水位，新的请求必须晚于该任务上次受理的请求时间；日志清理后即使时钟回拨也不会重放旧请求，客户端需保持时间正确。

`revision` 是当前运行配置摘要，与配置原文编辑用的 ETag 不同。禁用任务、未加载的新增任务不能执行；已有任务以 GET 返回的运行版本执行。受理后断开浏览器不会取消任务，网络失败时保留请求 ID，先用 GET 查询；404 也可能是并发提交尚未完成，不能据此换新 ID 重发。服务端不进行任何自动重试。

`tasks.changed` SSE 只发送不含正文的执行记录摘要；`tasks.paused` 表示任务存储写入失败。它们不替代持久化查询。

## 数据升级

数据库 schema 从 1 升至 2，新增任务游标与执行记录两张表及索引，不改动已有绑定 / 玩家表。迁移使用原有事务机制。旧 Core 会拒绝打开 schema 2；回退需同时恢复升级前的数据库备份，不能只换旧二进制或手改 `user_version`。首次启动新版前请保留停机后的一致性数据库副本及配置。
